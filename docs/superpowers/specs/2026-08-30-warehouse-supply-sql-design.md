# Склад, заявки и согласования в SQL

Спека к ТЗ владельца: перенести в базу листы `Склад`, `Лог`, `Номенклатура`,
`Заявки`, `Согласования` из таблицы «Склад».

Схема построена на фактических данных выгрузки от 30.08.2026, а не на догадках
по названиям колонок. Ниже сначала то, что выяснилось из данных и меняет
очевидные решения, потом сами таблицы.

## Что показали данные

### 1. «ID» в листе `Лог` — это ключ позиции, а не операции

Выглядит как идентификатор записи, но на деле повторяется: 274 строки, 272
уникальных значения, формат `Площадка|Ячейка|Наименование|Тип|Категория` —
то есть тот же составной ключ, что и `ID` в листе `Склад`.

Следствие: на него нельзя вешать защиту от повторной записи. Идемпотентный
ключ операции нужно завести отдельным полем (`request_id`) — фронт его уже
генерирует, см. `app/composables/useIdempotencyKey.ts`.

### 2. Остаток не выводится из лога — нужен начальный остаток

В листе `Склад` колонки `Поступление` и `Выдача` заполнены нулями во всех 273
строках, а `Остаток` — заполнен (например, «Аккум. батареи» = 2). В листе `Лог`
все 274 строки имеют действие `Прием` и `Кол-во = 0`: это первичный импорт
номенклатуры, а не движение.

То есть текущие остатки в лог не попадали и по нему не восстанавливаются.

Следствие: просто «считать остаток из лога» нельзя — это обнулит реальный
склад. Нужен явный начальный остаток на позицию, а лог применяется поверх него.

### 3. Номер счёта не уникален

В листе `Согласования` счёт `308/1` встречается дважды с разными суммами
(40 000,00 ₽ и 1,00 ₽). Значит `Счет` не может быть первичным ключом —
нужен свой суррогатный.

### 4. Колонки `Ожидает РО` / `Ожидает ГД` / `Согласован` / `Отменен` — не флаги

Внутри многострочный текст вида
`Колпино.ПТО.Инструменты.\n308/1 - 40 000,00 ₽\n\nОжидает РО` — это готовые
формулировки для показа и уведомлений, вычисляемые из остальных полей.

Следствие: в базе их не храним. Состояние несёт `Статус согласования` плюс даты
`Дата РО` / `Дата ГД` / `Отмена`; текст собирается на месте показа.

### 5. Суммы — форматированные строки

`"40 000,00 ₽"` — неразрывные пробелы, запятая как разделитель дробной части,
знак валюты. При импорте разбираем в `DECIMAL(15,2)`; хранить строкой нельзя,
иначе по суммам не посчитать и не отсортировать.

## Таблицы

Префикс `erp_`, как у существующих. Кодировка и движок — как в миграциях 001–006.

### `erp_warehouse_items` — номенклатура

Справочник товаров. Лист `Номенклатура` (`Наименование товара`, `Категория`).

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | |
| `name` | VARCHAR(255) | уникально |
| `category` | VARCHAR(255) | |
| `created_at` / `updated_at` | DATETIME(6) | |

`name` уникален: на него ссылаются остатки, лог и заявки.

### `erp_warehouse_stock` — остатки

Наличие ТМЦ на площадке. Лист `Склад`.

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | |
| `stock_key` | VARCHAR(512) | `Площадка\|Ячейка\|Наименование\|Тип\|Категория`, уникально |
| `platform` | VARCHAR(255) | |
| `cell` | VARCHAR(255) | ячейка хранения |
| `item_name` | VARCHAR(255) | |
| `item_type` | VARCHAR(64) | `Новый` / `Б/у` |
| `category` | VARCHAR(255) | |
| `unit` | VARCHAR(32) | |
| `opening_balance` | DECIMAL(15,3) | остаток на момент переноса (см. находку 2) |
| `created_at` / `updated_at` | DATETIME(6) | |

Колонок `Поступление`, `Выдача` и `Остаток` здесь **нет**. Причина: два
независимых источника одного числа расходятся, а расхождение по остаткам ТМЦ
дороже лишнего запроса. Текущий остаток считается так:

```
opening_balance + SUM(приход) - SUM(расход)   по erp_warehouse_log
```

Отдаётся представлением `erp_warehouse_balance`. `Поступление` и `Выдача` за
период — та же агрегация с фильтром по датам.

Если на реальных объёмах агрегат станет медленным — материализовать снимок,
пересчитываемый из лога, но не раньше, чем появятся цифры. Сейчас позиций 273.

### `erp_warehouse_log` — лог движений

Приход, расход и перемещение. Лист `Лог`. **Только добавление**: исправление
ошибки — компенсирующая запись, не UPDATE и не DELETE. Лог остаётся
единственным источником правды по движению и позволяет восстановить остаток
на любую дату.

| Поле | Тип | Комментарий |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | |
| `occurred_at` | DATETIME(6) | `Дата` |
| `platform` | VARCHAR(255) | |
| `action` | ENUM(`receipt`,`issue`,`transfer`) | `Прием` / `Выдача` / перемещение |
| `cell` | VARCHAR(255) | |
| `item_name` | VARCHAR(255) | |
| `item_type` | VARCHAR(64) | |
| `category` | VARCHAR(255) | |
| `quantity` | DECIMAL(15,3) | всегда положительное; знак задаёт `action` |
| `unit` | VARCHAR(32) | |
| `received_by` | VARCHAR(255) | `Принял` |
| `issued_by` | VARCHAR(255) | `Выдал` |
| `recipient` | VARCHAR(255) | `Получил` |
| `stock_key` | VARCHAR(512) | связь с позицией остатков |
| `request_id` | VARCHAR(64) NULL | ключ идемпотентности, уникальный |
| `created_at` | DATETIME(6) | |

`request_id` уникален (NULL допускается для строк первичного импорта, у которых
его нет). Это вторая линия защиты от задвоения: ответ GAS иногда терялся на
клиенте уже после записи, и повтор создавал вторую операцию.

Перемещение между площадками пишется двумя строками (`issue` с исходной,
`receipt` на целевой) с общим `request_id`-префиксом — одна строка не может
корректно уменьшить один остаток и увеличить другой.

## Переезд согласований: этапы

Сейчас лист работает в обе стороны — счета появляются в нём извне, а ERP пишет
обратно даты (`Дата РО`, `Дата ГД`, `Отмена`) и ведёт лист-журнал. Эти даты
почти наверняка читают вне ERP.

1. **Сейчас:** таблицы заведены, очередь читается из SQL, решение пишется
   и в SQL, и в лист (двойная запись). Поведение для внешних потребителей
   не меняется.
2. **После подтверждения владельца**, что лист больше никому не нужен, —
   отключить запись в лист.
3. **Последним шагом** — убрать GAS-мост.

Пока не выяснено: кто ещё читает лист и откуда будут появляться новые счета
после переезда (лист остаётся точкой ввода и синхронизируется — или в ERP
появляется экран создания счёта). До ответа лист остаётся точкой ввода.

## Границы

- Только стенд. Production на GAS, его не трогаем.
- Импорт реальных данных — с явного разрешения владельца. Складской контур
  стенда сейчас изолирован (одна тестовая категория «СИЗ»).
- Миграции — только в `public/api/migrations/`, начиная с 007.
