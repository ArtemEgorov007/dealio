# Согласования счетов: уход от сценария с гугл-таблицей — дизайн

> Продолжение `2026-08-28-invoice-approvals-design.md`, которая явно исключала
> «SQL-миграцию этого журнала» из v1. Это она.

## Цель и граница

Перенести процедуру согласования счетов с Google-таблицы на `erp_approvals`
(SQL) полностью: чтение очереди, видимость по этапу, решения, аудит «кем и
когда», уведомления на каждой смене статуса.

Входит: форма блока счёта, сценарий уведомлений, условия видимости у
согласующего.

Не входит: прод-деплой. Прод не тронут этой задачей вообще — деплой на него
отдельный ручной шаг (`workflow_dispatch`, `target: production`), и текущая
merge-в-main автоматика на него не попадает.

## Почему сейчас это возможно резать без синхронизации назад

`erp_approvals` пишется при создании счёта (`erp_supply_work_create_invoice`)
уже сегодня — двойная запись «SQL + лист» никогда не была реализована с этой
стороны, писался только SQL. Значит счета, заведённые новым сценарием
снабжения, **уже не появляются в листе** — согласующие их физически не видят,
потому что `erp_approvals_current`/`erp_approvals_decide` по-прежнему читают и
пишут исключительно через Apps Script bridge (`erp_approvals_bridge()` в
`Push.php`/`Approvals.php`, `gas/approvals-bridge/Code.gs`). Это не гипотеза —
факт, подтверждённый чтением кода: `erp_approvals_current` не проверяет
`ERP_BACKEND_MODE` и не читает `erp_approvals` вообще.

Внешних потребителей листа «Согласования» и аудит-листа «— журнал
согласований» нет (подтверждено пользователем) — переносить можно без
обратной синхронизации.

## Архитектура: мост убирается из кода

`erp_approvals_current`/`erp_approvals_decide` читают и пишут `erp_approvals`
напрямую. Функции моста (`erp_approvals_bridge`, `erp_approvals_bridge_config`,
`erp_approvals_decode_bridge`, `erp_approvals_queue_response`) удаляются из
`Approvals.php`. `erp_push_notify_pending_approvals` (крон-напоминание) тоже
переходит на прямой SQL-запрос вместо цикла `erp_approvals_bridge('queue', …)`
по каждому согласующему.

Файлы `gas/approvals-bridge/Code.gs` и `scripts/erp-approvals-bridge.gs**` не
удаляются — исторический артефакт, безопасный, потому что прод их всё ещё
использует до отдельного ручного переключения; ничего в новом коде на них не
ссылается.

Тумблер SQL/GAS не заводится: живого потребителя нет (прод эту задачу не
получает), а держать два рабочих сценария одной и той же логики — постоянная
цена без пользы.

## Модель данных

Новая миграция `019_erp_approvals_sql_native.sql`, поверх существующей
`erp_approvals` (008 + 011):

```sql
ALTER TABLE erp_approvals
    -- Кто завёл счёт — этой колонки нет вовсе. Без неё уведомлять
    -- «Инженеру снабжения» (п.7 ТЗ) некого. Тот же приём снимка, что в
    -- erp_work_objects/erp_work_log: увольнение автора не должно обнулять
    -- историю уже созданных счетов.
    ADD COLUMN created_by BIGINT UNSIGNED NULL AFTER approver_fio,
    ADD COLUMN author_fio VARCHAR(255) NOT NULL DEFAULT '' AFTER created_by,
    -- Кто согласовал на этапе ГД и кто отклонил — старый Apps Script вёл
    -- отдельный аудит-лист с ФИО на каждое решение; в SQL этой возможности
    -- пока нет вообще, а «кем и когда» (п.4 ТЗ) без неё неполно на втором
    -- этапе.
    ADD COLUMN approved_gd_fio VARCHAR(255) NULL AFTER approved_gd_at,
    ADD COLUMN rejected_by_fio VARCHAR(255) NULL AFTER cancelled_at,
    -- Тот же паттерн diff'а, что уже проверен на erp_supply_requests: крон
    -- уведомляет только по расхождению status <> notified_status и метит
    -- отправленным даже при сбое доставки — иначе бесконечный повтор.
    ADD COLUMN notified_status VARCHAR(64) NOT NULL DEFAULT '' AFTER status,
    ADD CONSTRAINT erp_approvals_author_fk
        FOREIGN KEY (created_by) REFERENCES erp_users (id) ON DELETE SET NULL;
```

`erp_approval_notifications.approval_row_number` и `erp_push_sent.approval_row_number`
**не трогаются** — при планировании нашёлся реальный конфликт: обе колонки
переиспользует `erp_approvals_notify_all_with_access()` (тестовая рассылка
«всем согласующим») с синтетическим отрицательным номером
(`-1 * ($userId * 10000 + $broadcastStamp)`), который никогда не был и не
будет строкой `erp_approvals` — FK на них немедленно ломает эту рассылку.
Задача не просила чистить эти таблицы, ТЗ про сценарий согласования, а не про
внутренний трекинг рассылок — оставляю как есть.

`approved_ro_at`/`approved_gd_at`/`cancelled_at` остаются `DATE` — тип не
меняется, клиент (`invoices.vue`) уже форматирует их как дату без времени, и
менять его ради этой задачи незачем.

Статусы — литералы из текста ТЗ:

```php
const ERP_INVOICE_STATUS_NEW = 'Ожидает РО';       // уже есть
const ERP_INVOICE_STATUS_PENDING_GD = 'Ожидает ГД';
const ERP_INVOICE_STATUS_APPROVED = 'Согласован ГД';
const ERP_INVOICE_STATUS_REJECTED = 'Отклонен';
```

`rowNumber` переименовывается в `id` в API-ответе, TS-типе `ErpApproval` и
клиентских компонентах (`ErpApprovalCard`, `approvals.vue`) — не в
`erp_approval_notifications`/`erp_push_sent` (см. ниже, почему их колонка
остаётся `approval_row_number`). Решение пользователя: «имя больше не
соответствует сути» перевешивает размер диффа там, где это не ломает ничего
постороннего.

## Видимость и право решать

Переносится один в один из `gas/approvals-bridge/Code.gs` — это рабочие
правила бизнеса, а не техническая деталь реализации, которую можно
переизобрести:

- этап РО виден и решаем **только** тем, чьё ФИО совпадает с `approver_fio`
  счёта (этот человек выбран при заведении счёта — `erp_supply_work_create_invoice`
  уже проверяет, что у него есть право `approvals`);
- этап ГД виден и решаем **любому**, чья `position` точно равна
  `Генеральный директор` — по должности, не по конкретной привязке к одному
  человеку. Нормализация должности (`erp_approvals_position()`) уже есть в
  `Approvals.php` и переиспользуется как есть; сам предикат
  `erp_approvals_is_director()` — новая тонкая обёртка над ней, порт
  `isDirector_()` из `.gs`, которого в PHP пока нет;
- отклонить может тот же, кому сейчас назначено решение — ответственный на
  активном этапе, а не любой обладатель права `approvals` вообще. Формулировка
  ТЗ «любой согласующий может отклонить» читается как «любой из двух
  возможных ответственных на этот счёт» — так было в старой логике
  (`approvalActorResponsible_`), и это осмысленно: иначе случайный согласующий
  мог бы отклонить чужой счёт, который ему даже не показан.

**Идемпотентность и конфликты** переносятся из `.gs` как есть — там разбор был
не «409 всегда», а три исхода:

| Ситуация | Ответ |
| --- | --- |
| Счёт сейчас на этапе этого actor'а и ещё не решён | решение проходит |
| Тот же actor уже поставил решение на своём этапе (двойной тап) | `already_processed`, не ошибка |
| Отклонить, а счёт уже согласован хоть на каком-то этапе (`approved_ro_at`/`approved_gd_at` не пусто) | 409 «Строка изменилась…» |
| Согласовать, а счёт уже отклонён | 409 «Строка изменилась…» |
| Actor не ответственен за текущий этап счёта вовсе | 403 |

Одним `UPDATE ... WHERE status = :expected` эти три исхода не различить —
нужен `SELECT ... FOR UPDATE` внутри транзакции (актуальный статус + оба поля
дат), по нему принимается решение, какой из пяти веток выше вернуть, и только
затем `UPDATE`. Ответственность/видимость проверяется до входа в транзакцию —
как и сейчас.

## Сценарий и уведомления — мгновенно, не через 5-минутный крон

Тот же приём, что уже в `erp_supply_work_create_invoice` («Автор заявки узнаёт
о смене статуса сразу, а не через пять минут крона»):

1. Инженер снабжения создаёт счёт → статус `Ожидает РО` (уже так) → пуш
   назначенному согласующему РО.
2. РО согласовал → статус `Ожидает ГД`, на блоке счёта появляется «Согласовано
   {approver_fio}, {approved_ro_at}» → пуш всем действующим ГД (по должности).
3. ГД согласовал → статус `Согласован ГД`, `approved_gd_fio` заполнен, цепочка
   закончена.
4. Отклонение на любом этапе (РО или ГД) → статус `Отклонен`,
   `rejected_by_fio` заполнен, цепочка закончена.
5. На **каждую** из этих смен статуса (1–4) — отдельно пуш автору счёта
   (`created_by`/`author_fio`), тем же diff-механизмом `notified_status`, что
   уже проверен на `erp_supply_requests`. Крон
   (`POST /internal/approvals-notify-status`, новый роут, тот же
   `erp_require_cron_token`) — подстраховка на случай, если мгновенная
   отправка не удалась; расписание — как у существующих `push-notify-*`
   (каждые 5 минут, см. `docs/sql-staging-deploy-runbook.md`).

Бейдж на плитке и в таббаре — без изменений в клиенте: `approvalsStore.pendingCount`
как и сейчас читается из `GET /approvals`, просто теперь ответ считается по
SQL (`SELECT COUNT(*) ... WHERE status = ...` для актуального этапа
пользователя), а не по длине массива из bridge.

## PDF в iframe

`ErpInvoiceViewer` уже рендерит iframe по `invoiceUrl` с https-only проверкой
(п.8 ТЗ закрыт готовым компонентом, трогать не нужно). Меняется только
источник самой ссылки: вместо `Ссылка на счет` из листа —
`/supply-work/invoices/{id}/file`, тот же маршрут, что уже отдаёт файл на
экране «Все счета». Этот маршрут сейчас закрыт правом `supply`
(`erp_supply_work_invoice_file`) — открываю его также и для `approvals`,
иначе согласующий видит карточку счёта, но не может посмотреть сам PDF.

## Видимость всех счетов инженеру снабжения (п.9 ТЗ)

Уже реализовано: `erp_supply_work_invoices` (маршрут «Все счета») отдаёт все
строки `erp_approvals` без фильтра по этапу, за правом `supply`. Изменений не
требует — только новые колонки (`approved_gd_fio`, `rejected_by_fio`) в ответ
для полноты карточки.

## Тестирование и проверка

- контрактные тесты: `tests/approvals-contract.test.mjs` перепишется —
  вместо проверки конфигурации моста проверяет видимость по этапу/должности,
  запрет отклонения не-ответственным, литералы статусов, наличие миграции 019,
  переименование `id`;
- новый прогон на живом MySQL (как во всех предыдущих задачах сессии):
  сквозной сценарий — создание счёта → пуш РО → согласование РО (статус,
  приписка, пуш ГД + пуш автору) → согласование ГД (статус, `approved_gd_fio`,
  пуш автору) → отдельно отклонение на каждом этапе → попытка решить чужой
  счёт (403/404) → повторное решение уже решённого (409);
- мобильный и десктопный тач-проход по ТЗ (обязательный пункт приёмки),
  включая просмотр PDF в iframe;
- `staging-audit.sh` + факт удаления вызовов `erp_approvals_bridge` из
  реального пути (grep по собранному API на staging, как в прошлых задачах);
- `advisor`-гейт перед «ПРИНЯТО» — обязателен по правилам репозитория.

## Явно не входит в эту задачу

- прод-деплой;
- удаление `.gs`-файлов моста;
- SQL-миграция полей `Промеры`/другие листы, не относящиеся к согласованиям;
- изменение состава/суммы/площадки уже созданного счёта.
