# Каталог бирок ERP — спецификация первого релиза

Дата: 2026-08-27  
Контур: только staging `erp-mt.online` до отдельного решения о production

## Решение

Менеджер создаёт новый раздел/титул в ERP, выбирает площадку и цех, вставляет
список бирок (одна строка — одна бирка), сначала видит проверку, затем
подтверждает импорт. CSV и прямое редактирование существующего каталога не
входят в первый релиз.

Google Sheets остаётся источником для уже существующего Google-каталога.
Новые записи, созданные в ERP, получают источник `erp` и не могут быть
архивированы фоновым Google → SQL sync. Так исключается остановка процесса и
не возникает ситуация, в которой sync уничтожает только что созданный титул.

После приёмки нового экрана все **новые** титулы создаются через ERP. Google
переходит в роль наследуемого источника и резервной выгрузки, но не второго
равноправного места для создания новых SQL-титулов.

## Цели

1. Создавать новый титул и его набор бирок без SQL-консоли и Google Sheets.
2. Не допускать дублей внутри вставленного списка и в активном SQL-каталоге.
3. Сохранять автора, время, результат и состав импорта в SQL-аудите.
4. Не ломать выдачу, сдачу, существующий Google bridge и историю операций.
5. Давать доступ к созданию каталога только менеджеру с правом работы с
   бирками.

## Не входит в релиз

- CSV/XLSX-загрузка и распознавание произвольных файлов.
- Удаление или массовое редактирование уже выданных бирок.
- Переключение production на SQL.
- Двусторонняя синхронизация SQL → Google.
- Склад, упаковка и промеры.

## Модель данных

### Титулы

Новая таблица `erp_badge_titles`:

- `id` — внутренний идентификатор;
- `title_name` — название титула/раздела;
- `platform` — площадка;
- `workshop_id` — цех (`kolpino` или `volkhonka`);
- `status` — `active` / `archived`;
- `created_by` — ссылка на `erp_users`;
- `created_at`, `archived_at`.

Название титула уникально в пределах пары «площадка + цех» среди активных
титулов. Повторный импорт в существующий титул не входит в первый релиз:
ошибка требует создать корректно названный титул либо дождаться следующей
волны редактирования.

### Бирки

В `erp_workshop_badges` добавляются:

- `title_id` — nullable FK на `erp_badge_titles`; у наследуемых Google-бирок
  остаётся `NULL`;
- `catalog_source` — `gas` или `erp`, по умолчанию `gas` для уже импортированных
  строк;
- `created_by` — nullable FK на автора ERP-вставки.

Текущий уникальный ключ `(workshop_id, badge_hash)` сохраняется. Одна и та же
бирка не может попасть в два активных титула одного цеха.

### Аудит импорта

Новая таблица `erp_badge_import_batches` хранит:

- созданный титул, площадку и цех;
- автора и время;
- количество входных, добавленных, пустых и дублирующихся строк;
- idempotency key и итоговый статус (`completed` / `rejected` / `failed`).

Содержимое бирок не дублируется в аудите: оно уже находится в каталоге. Это
уменьшает риск утечки и рассинхронизации.

## Правило bridge-синхронизации

Google → SQL sync продолжает создавать и обновлять только строки с
`catalog_source = 'gas'`.

- Строки `catalog_source = 'erp'` никогда не архивируются при отсутствии в
  Google.
- Если Google содержит бирку, ранее добавленную в ERP в том же цехе, sync не
  перезаписывает её и фиксирует конфликт счётчиком в своём audit run.
- Ошибка fetch/DB-транзакции не меняет ни Google-, ни ERP-каталог.

Это даёт переходный период без двух источников для одной и той же записи.

## Доступ и API

Все endpoints требуют действующую серверную сессию. Создание, preview и
просмотр аудита требуют одновременно:

1. роль `Менеджер`;
2. право `badges`.

Исполнитель, даже с правом выдачи бирок, получает `403` для всех catalog API.

Предлагаемые endpoints:

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/badge-catalog/titles` | список активных ERP-титулов и счётчики |
| `POST` | `/api/badge-catalog/preview` | валидация формы без записи |
| `POST` | `/api/badge-catalog/imports` | атомарное создание титула и бирок |
| `GET` | `/api/badge-catalog/imports` | журнал завершённых импортов |

`preview` принимает `titleName`, `platform`, `workshop`, `badgesText`.
Разбор: trim, одна непустая строка — одна бирка; порядок строк сохраняется.

`imports` повторяет проверку на сервере, использует `idempotencyKey` и в одной
транзакции создаёт титул, строки каталога и audit batch. Клиентское preview
никогда не считается доказательством валидности: между preview и confirm
может появиться новый импорт.

## Интерфейс

В разделе «Бирки» для менеджера добавляется действие **«Каталог»**. Экран:

1. список последних импортов и активных титулов;
2. кнопка «Новый титул»;
3. форма: название, площадка, цех, большое поле «Бирки — по одной на строку»;
4. кнопка «Проверить»;
5. результат: сколько будет добавлено, какие строки пустые/повторяются и
   какие уже есть в каталоге;
6. кнопка «Подтвердить импорт» активна только при отсутствии ошибок;
7. результат импорта с количеством добавленных бирок и ссылкой на титул.

Исполнитель не видит входа в каталог. Ошибки не раскрывают содержимое чужих
импортов или технические детали БД.

## Приёмка staging

1. Менеджер создаёт новый титул с валидным списком — в SQL появляются title,
   badge rows и completed audit batch.
2. Повтор внутри списка блокирует confirm и показывает номер строки.
3. Уже существующая активная бирка блокирует confirm.
4. Повторная отправка одного idempotency key не создаёт второй титул.
5. Исполнитель получает `403` на preview/import/audit.
6. Google sync после ERP-импорта не архивирует ERP-бирки.
7. Google-бирки всё ещё появляются в SQL после sync и могут архивироваться
   только как Google-строки.
8. Выдача принимает новую ERP-бирку, а неизвестную — отклоняет.
9. Ошибка записи откатывает и титул, и все его бирки.
10. Ручной mobile/desktop QA подтверждает форму, preview, ошибки и журнал.

## Rollout

1. Реализация и тесты локально.
2. Миграция и API на staging.
3. Первый тестовый титул и его полная отмена/архивация на staging.
4. Параллельная проверка с Google bridge минимум несколько рабочих смен.
5. Отдельная приёмка для production; без неё production остаётся GAS.
