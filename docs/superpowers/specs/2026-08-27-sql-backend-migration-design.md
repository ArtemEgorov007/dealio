# SQL Backend Migration Design

## Goal

Перевести ERP с нестабильных клиентских вызовов Google Apps Script на same-origin PHP API и MySQL без потери текущих операционных данных и без переключения production до успешного staging QA.

## Scope

Первый выпуск SQL-контура покрывает аутентификацию, сотрудников и права, счётчики смены, бирки, сдачу и склад. Google Sheets после переключения не принимает рабочие изменения: она используется как резервный экспорт и инструмент сверки на время миграции.

## Current-State Findings

- На текущем хостинге доступны PHP 8.3 FastCGI и локальный MySQL 8.0 для обоих ERP-доменов.
- В существующей БД есть четыре InnoDB-таблицы: сотрудники, СМР, договоры и номенклатура; данные уже внесены.
- Существующая таблица сотрудников хранит пароль открытым текстом, не имеет уникального ограничения для логина и пригодна только как источник импорта, а не как таблица аутентификации.
- СМР уже содержит рабочие записи, поэтому исходные таблицы не изменяются и не переименовываются в рамках миграции.

## Options Considered

1. Оставить GAS и добавить повторные попытки. Это быстро, но не устраняет зависимость от Google-авторизации и нестабильных редиректов.
2. Подключить фронтенд напрямую к MySQL. Отклонено: это раскрывает доступ к БД и не даёт серверной авторизации.
3. Развернуть PHP API на том же хостинге и подключать его к MySQL по локальному соединению. Выбрано: API скрывает учётные данные БД, даёт единые правила авторизации и не требует нового провайдера.

## Architecture

Nuxt остаётся статическим клиентом. На каждом домене API размещается по пути `/api`; staging и production имеют изолированные конфигурации. PHP API использует PDO, отдаёт только JSON, проверяет сессию и права до обращения к данным. Клиент не получает реквизиты БД и не обращается к Google Apps Script в SQL-режиме.

Пароль при импорте преобразуется в `password_hash()` и исходное значение не сохраняется в новых таблицах. После первого успешного входа пользователь продолжает работать через защищённую cookie-сессию. При любой ошибке API возвращает код и безопасное сообщение; детали пишутся в серверный журнал без паролей и персональных данных.

## Data Model

Новые таблицы получают префикс `erp_`, чтобы не изменить существующие таблицы:

- `erp_users`: UUID/целочисленный идентификатор, ФИО, логин с UNIQUE, `password_hash`, роль, площадка, статус, даты создания/изменения.
- `erp_user_permissions`: пользователь, код права, значение; уникальная пара пользователь/право.
- `erp_sessions`: хэш токена, пользователь, время истечения, отзыв сессии.
- `erp_shift_events`: тип события (бирка/сдача), пользователь, площадка, ссылка на бизнес-запись, время; основа ролевых счётчиков.
- `erp_audit_log`: актор, действие, сущность, идентификатор, время, технический request ID; без паролей и значений секретных полей.

Рабочие данные СМР, договоров и номенклатуры на первом этапе читаются через адаптеры поверх существующих таблиц. Перед переводом записи они получают отдельные ключи и подходящие типы в новых `erp_*` таблицах; прежние таблицы остаются неизменным источником сверки до завершения миграции.

## API Boundaries

- `POST /api/auth/login`: проверка логина/пароля, выдача защищённой сессии.
- `POST /api/auth/logout` и `GET /api/auth/me`: управление и восстановление сессии после перезагрузки.
- `GET /api/personnel/departments`, `GET /api/personnel/employees`, `GET /api/personnel/employees/{id}`: кадровый экран.
- `PATCH /api/personnel/employees/{id}`, `POST /api/personnel/employees`, `POST /api/personnel/employees/{id}/dismiss`: кадровые изменения, только для права управления кадрами.
- `GET /api/shift-counters`: исполнитель получает только свои события за смену; менеджер — события площадки за смену.
- Модули бирок, сдачи и склада получают собственные endpoints и серверную идемпотентность до их переключения с GAS.

Все write-endpoints требуют CSRF-защиты/проверки Origin, серверной проверки роли и права, идемпотентного ключа для операций, которые создают проводку, и записи в аудит.

## Migration and Release

1. Сделать резервную экспортную копию существующих таблиц и зафиксировать количество строк.
2. Создать только новые `erp_*` таблицы в staging-конфигурации; старые таблицы не менять.
3. Импортировать сотрудников и права, хэшируя пароли; сверить количество, уникальность логинов и права.
4. Включить API в staging, прогнать контрактные, интеграционные и ручные сценарии менеджера и исполнителя.
5. Сравнить счётчики и выборочные данные с исходным контуром, устранить расхождения.
6. Повторить миграцию production из свежей резервной копии только после отдельного подтверждения пользователя; иметь обратимое переключение флага API/GAS.

## Acceptance Criteria

- Перезагрузка страницы не завершает действующую сессию.
- Менеджер видит и редактирует только разрешённые кадровые данные; исполнитель видит только собственные счётчики смены.
- Логин уникален, пароль не хранится и не возвращается в открытом виде.
- Каждая создающая операция идемпотентна и попадает в аудит.
- Все staging сценарии проходят дважды подряд без ошибки связи с Google.
- Production не меняется до резервного экспорта, успешного QA и отдельного подтверждения на выпуск.

## Out of Scope

Изменение действующих исходных таблиц, удаление Google Sheets, перенос исторических данных без сверки, прямой доступ фронтенда к MySQL и выпуск production в рамках первого SQL-этапа.
