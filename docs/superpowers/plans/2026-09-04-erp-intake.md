# Приход: приёмка объектов выполнения работ

**Спека:** ТЗ «Приход: функционал для фиксации поступления на площадку объектов выполнения работ» (два сценария, полный текст — в задаче). Собственный дизайн Sonnet, без отдельного design-doc: разведка существующей схемы (`erp_work_objects`, `erp_work_log`, паттерн уведомлений) + два раунда ревью advisor (архитектура, затем — гонки/IDOR/идемпотентность).

## Реализовано

- Новое право `intake` («Доступ к приходу»), раздел «Приход» — по устоявшемуся в репо шаблону (тот же, что у orders/supply/contracts): `Auth.php`, `types/erp.types.ts`, `erp-sections.ts`, `erp-flow.global.ts`, `Personnel.php` (метка для «Кадров»).
- Миграция `021_erp_intake.sql`: `erp_intake_deliveries` (заголовок поставки — фото/накладная/вес/площадка/автор, общая на оба сценария), `erp_intake_delivery_files` (фото 1:1, тот же приём, что `erp_invoice_files`), `erp_intake_delivery_objects` (join на принятые марки, сценарий 1 only).
- `public/api/src/Intake.php` — 5 обработчиков, сценарии 1 и 2 целиком.
- 3 страницы (`intake.vue`, `intake-objects.vue`, `intake-unmatched.vue`) + `erp-intake.ts`.

## Известные ограничения (осознанно, не баг)

- **Фото до 8 МБ (`ERP_INTAKE_PHOTO_MAX_BYTES`) опирается на серверный `max_allowed_packet` ≥ 16M** — тот же лимит уже используется для PDF-счетов (`ERP_INVOICE_MAX_BYTES` в `SupplyWork.php` → `erp_invoice_files`), эта фича живёт на проде с BLOB-вставками такого размера без зарегистрированных сбоев. Если когда-нибудь всплывёт `SQLSTATE[08S01]`/обрыв соединения на большом фото — это `max_allowed_packet`, не баг кода; чинить на сервере, не понижением константы вслепую.
- **Фото/накладная/дата поступления сейчас write-only** — ТЗ требует их хранить, но не требует экрана просмотра, и его нет. Если понадобится — отдельная задача.
- **`department = 'ПТО' OR position LIKE '%ПТО%'`** — в системе нет справочника отделов; если реальные данные используют третью формулировку, список сценария 2 может недосчитаться сотрудника. Проверить на живых данных при первой жалобе.

## Обзоры advisor

1. Архитектура (общая таблица-заголовок на оба сценария; «рабочая ведомость» = `erp_work_objects`; площадка только из профиля) — согласовано без правок.
2. Первый разбор кода — 7 находок (TOCTOU статуса поставки, неидемпотентный шаг 2, молчаливая потеря марок при частичном приёме, IDOR, `title=NULL`→ложный конфликт, отсутствие валидации длины/веса, вопрос про `max_allowed_packet`) — все закрыты.
3. Повторный разбор — нашёл, что фикс идемпотентности шага 2 конфликтовал с фиксом частичного приёма (повтор после частичного приёма отдавал 409 вместо честного `skippedIds`) и что повтор `unmatched` сверял только титул, не ФИО ПТО (переназначение отвечало тихим 200) — оба закрыты, перепроверено живым MySQL.
