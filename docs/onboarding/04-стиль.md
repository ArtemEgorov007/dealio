# Стиль и соглашения

Правило одно: **новый код должен читаться как соседний**. Всё ниже — не вкусовые
предпочтения, а описание того, что уже в репозитории.

---

## Комментарии

Комментарий объясняет **почему**, а не что. «Что» видно из кода.

```ts
// Плохо: пересказ кода
// Фильтруем позиции по запросу
const found = filterByQuery(items, query, i => i.name)

// Хорошо: причина решения
// Слова сверяются независимо и в любом порядке: «защитная каска» не находила
// «Каска защитная», и сотрудник решал, что позиции в номенклатуре нет.
```

Особенно ценно комментировать:

- почему выбран неочевидный вариант, и чем плох очевидный;
- ограничение платформы (`!important` против зума iOS);
- случай, который уже ломался в проде.

Комментарии на русском, как и весь проект.

## Именование

Функции и переменные — по смыслу предметной области, а не по механике.
`erp_supply_next_code`, `unresolvedRows`, `isBrowsingAll` — понятно без контекста.

PHP-функции API: префикс `erp_` и домен — `erp_supply_*`, `erp_warehouse_*`,
`erp_push_*`. Таблицы БД: префикс `erp_`, это проверяется тестом.

Vue-компоненты подключаются автоимпортом по пути: `components/ui/button/Button.vue`
становится `<UiButton>`, `components/erp/ErpScreen.vue` — `<ErpScreen>`.
Утилиты из `app/utils/` доступны без импорта.

## Дублирование

Один факт живёт в одном месте. Разъехавшиеся копии — главный источник багов
здесь: два каталога миграций, три дословных копии проверки cron-токена,
скопированный по четырём экранам поиск по списку. Всё это уже чинили.

Если один и тот же приём появился в третий раз — выноси.

## Тесты

Контрактные тесты (`tests/*.test.mjs`) в основном **читают исходник** и
проверяют, что решение на месте. Это осознанный выбор: фронтенд не покрыт
рантайм-тестами, а зафиксировать «почему именно так» надо.

Из этого следуют два правила.

**Название теста — утверждение о поведении, а не о коде.**

```js
// Плохо
test('в supply.vue есть pointerdown', ...)

// Хорошо
test('выбор позиции работает касанием, а не только мышью', ...)
```

**В тесте объясняй, что сломается без него.** Тест — последнее место, где
живёт причина решения:

```js
test('поле количества не растёт после выбора позиции', () => {
    // Сетка по умолчанию растягивает ячейки на высоту строки: когда под
    // номенклатурой появлялась подпись категории, поле количества
    // вытягивалось с 46 до 65px (замерено на стенде).
    assert.match(fields, /align-items: start/)
})
```

Такой тест сохраняет знание. «Проверяем, что есть align-items» — нет.

**Помни, чего они не ловят.** Всё поведенческое: тип значения из `v-model`,
события касания, перекрытие клавиатурой. Для этого — ручной проход,
[`02-локальный-стенд.md`](02-локальный-стенд.md).

Для чистой логики (`app/utils/`) тесты настоящие: модуль загружается через
`tests/helpers/load-ts.mjs` тем же компилятором, что и сборка.

Тесты PHP — в `tests/php/`, запускаются вместе со всеми через `npm run verify`.

## Стили

sass, БЭМ-подобные имена внутри компонента: `.supply-row__category`,
`.req-card__status--warn`. Цвета — из переменных `app/assets/css/variables.css`,
не хардкодом.

Перед добавлением своего правила проверь, не перебьёт ли его глобальное из
`erp-theme.css`: там есть `!important` для полей ввода, и своё `font-size`
просто не применится.

## Коммиты

Заголовок — что сделано, в повелительном наклонении, с областью:
`fix(erp): поле количества растягивалось после выбора позиции`.

Тело — **почему это правильно** и чем подтверждено. Замеры, вывод команды,
условия воспроизведения. Такой коммит потом отвечает на вопрос «почему тут так»
без раскопок.

Плохо: `fix: исправил баг с инпутом`.
Хорошо: см. историю — там есть образцы с замерами до/после.

## Сообщения пользователю в интерфейсе

Пишем от лица того, кто смотрит на экран, а не от системы. Ошибка объясняет, что
произошло и что сделать: «„Выдуманная штука“ нет в номенклатуре склада —
выберите позицию из списка», а не «invalid_input».

Кнопка называется тем, что произойдёт, и это же слово повторяется в результате.
