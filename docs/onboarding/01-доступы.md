# Карта доступов

> **Здесь нет ни одного пароля и не должно появиться.**
> Репозиторий на GitHub. Этот файл отвечает на вопрос «что вообще существует и
> где взять», а значения живут в приватном файле и в менеджере паролей.
>
> Заполненный файл со значениями: `доступы.local.md` рядом с этим — он в
> `.gitignore`. Шаблон: [`доступы.local.example.md`](доступы.local.example.md).
> Скопируй шаблон, заполни из менеджера паролей, и он останется только на твоей
> машине.

Владелец всех учётных записей — заказчик (KINTECH GROUP / «Морфлот
Технология»). При смене исполнителя доступы **перевыпускаются**, а не
передаются перепиской.

## Что существует

| Доступ | Где хранится значение | Зачем нужен |
|---|---|---|
| **reg.ru** — домены и хостинг | менеджер паролей заказчика | DNS, продление доменов, SSL |
| **ISPmanager** — панель хостинга | менеджер паролей | shell-клиент, файловый менеджер, CRON, phpMyAdmin |
| **FTP (обычный)** | менеджер паролей | заливка серверных скриптов в `/erp-ops` |
| **FTP (деплойный)** | GitHub Environments | используется только CI, руками не нужен |
| **MySQL** | приватный конфиг на сервере | база стенда и прода |
| **Тестовый сотрудник ERP** | менеджер паролей | вход в приложение для проверки |
| **GitHub** | личная учётка исполнителя | код, PR, Actions |
| **Google Apps Script** | учётка владельца таблиц | legacy-бэкенд, пока не отключён |
| **VAPID-ключи push** | приватный конфиг на сервере | web-push уведомления |
| **Токен cron** | приватный конфиг на сервере | защита внутренних маршрутов рассылки |

## Хостинг: как устроено

Виртуальный хостинг reg.ru, один аккаунт на оба сайта.

```
<домашний каталог>/            ← корень FTP-подключения
├── www/
│   ├── erp-mt.online/         ← СТЕНД: сюда выкладывает CI
│   ├── erp-mt.ru/             ← ПРОД: выкатка только вручную
│   └── erp-api-private/       ← приватный конфиг API, ВНЕ webroot
│       └── erp-api-config.php ← доступ к БД, VAPID-ключи, cron-токен
└── erp-ops/                   ← серверные скрипты и рабочие файлы
    ├── scripts/               ← CLI: миграции, импорт, рассылки
    ├── import/                ← исходники импорта
    └── *.log, *.lock          ← логи и локи кронов
```

**Важная ловушка.** Корень FTP и корень shell — не одно и то же. В shell-клиенте
ISPmanager домашний каталог отдаёт `pwd`, и путь `/erp-ops/...`, который ты
видишь по FTP, в shell пишется как `$HOME/erp-ops/...`. Абсолютный `/erp-ops`
не существует и даёт «Could not open input file».

**Приватный конфиг** `www/erp-api-private/erp-api-config.php` лежит на уровень
выше сайтов, поэтому не отдаётся по HTTP. Его ищет `erp_load_config()` в
`public/api/src/Database.php`. В нём: DSN и пароль MySQL, VAPID-ключи, cron-токен.
Копии этого файла в репозитории нет и быть не должно.

## GitHub

Секреты и переменные — в **Settings → Environments**, отдельно для `staging` и
`production`. Полный список и требования к настройке: [`../deployment.md`](../deployment.md).

Коротко: `SFTP_HOST`, `SFTP_USERNAME`, `SFTP_PASSWORD`, `SFTP_KNOWN_HOSTS` —
секреты; `SFTP_PORT`, `SFTP_SERVER_DIR`, `DEPLOY_URL`, `ERP_BACKEND_MODE`,
`ERP_API_BASE` — переменные.

`ERP_BACKEND_MODE` задан только у `staging` (значение `sql`). У `production` он
не задан намеренно: workflow подставляет `gas`, и прод остаётся на старом
бэкенде до отдельного решения о переключении.

## Если доступы потеряны

1. **Хостинг и домены** — восстанавливаются через личный кабинет reg.ru
   владельцем аккаунта. Почта аккаунта известна заказчику.
2. **Приватный конфиг API** — единственная копия живёт на сервере. Если сервер
   цел, конфиг можно прочитать через shell-клиент ISPmanager. Если утерян и он:
   доступ к БД перевыпускается в панели, VAPID-ключи генерируются заново
   (`scripts/generate-vapid-keys.py`), но **все существующие push-подписки
   станут недействительны** — сотрудникам придётся заново разрешить уведомления.
3. **GitHub-секреты** — не читаются после сохранения, только перезаписываются.
   Значения берутся из хостинга заново.
4. **База** — резервные копии делает хостинг (раздел «Резервные копии» в
   ISPmanager). Схема воспроизводится миграциями из `public/api/migrations/` на
   пустой базе; данные — только из бэкапа.

## Чего нельзя делать

- Класть значения в репозиторий, в описание задачи, в сообщение коммита.
- Слать пароли в мессенджер. Если пришли — считать скомпрометированными и
  просить заказчика перевыпустить.
- Использовать личную почту исполнителя для рабочих регистраций.
- Держать прод-доступы в том же файле, что и стенд, без пометки: перепутанное
  окружение — самая дорогая ошибка здесь.
